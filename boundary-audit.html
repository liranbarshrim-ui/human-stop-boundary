Decision Authority Record · Boundary Audit v1.0

Does the refusal actually bind?

A named refusal is not enough. The audit traces authority from its origin through the refusal event and release decision to the defined protected effect, then tests whether another path can produce that effect without the required authority.

produce(p,e) ⇒ authorized_release(p,e)

This is the A11 effect invariant used as an audit question: for every execution path capable of producing protected effect e, production must require an authorized release.

Official definition

DAR Boundary Audit is an evidence-based examination of whether a system's refusal boundary remains binding from authority origin through release authorization to the defined protected effect, including verification that no alternate execution path can produce that effect without the required authority.

The boundary chain

01Authority OriginWhere does the authority come from, and who establishes it?
02RefusalWhat event activates the protected stop condition?
03ReleaseWho is authorized to release the stop, and how is that authority authenticated?
04Protected EffectWhat exact action, state transition, or material consequence is protected?
05Alternate PathCan another principal, session, interface, mandate, or internal path produce the same effect?

Nine core questions

Q1What exactly is the Protected Effect?Define target, action, state transition and material consequence.
Q2What event creates the Refusal boundary?Identify the trigger and the state in which continuation becomes conditional.
Q3Who is authorized to release it?Name the principal, not merely the role or team.
Q4What does that authority cover?Bind authority to the exact target, action and effect.
Q5How is the decision authenticated?Test identity, integrity, freshness and replay resistance.
Q6Where does Release Authority originate?Trace the authority root and its establishment mechanism.
Q7Can the system create or elevate authority itself?Test self-authorization, administrative widening and interpretation drift.
Q8Can another path produce the same effect?Test alternate principals, sessions, interfaces, mandates and internal paths.
Q9Is release required before effect?Verify the operational and cryptographic binding between release and effect.

Evidence discipline

The audit does not treat documentation as execution proof. Each material claim follows the chain:

CLAIM → MECHANISM → ENFORCEMENT POINT → EVIDENCE → REPRODUCTION → OBSERVED RESULT

Evidence is classified as VERIFIED, DECLARED, or UNRESOLVED. A missing proof is not silently converted into a PASS; an UNRESOLVED boundary is not called FAIL unless the prohibited capability is actually demonstrated.

Boundary determination

PASS

The required property is supported by reproducible evidence within the declared scope.

UNRESOLVED

The boundary or evidence is incomplete. The audit does not infer a failure from missing proof alone.

FAIL

The prohibited capability or bypass is demonstrated within the declared audit scope.

Test the claim, not the story.

Start with one protected effect. Name the release authority. Then try to reach the same effect without it.
